# Codex 项目指令迁移说明

> 迁移来源：`Claude_Projects指令V3.6.md`
> Codex 入口：仓库根目录 `AGENTS.md`
> 迁移日期：2026-07-13
> 状态：已升级为 Claude Desktop + Codex 双管理架构，待实际任务回归验证

## 一、迁移目标

这次迁移不是把 Claude 指令简单改名，而是把其中不同层级的规则拆开：

1. 长期稳定、每个任务都可能需要的规则进入根目录 `AGENTS.md`。
2. 只在写作、RAG 或知识治理任务中需要的详细步骤继续留在现有 SOP，由 `AGENTS.md` 按条件要求读取。
3. Claude Projects 的历史上传快照和 GitHub 不再作为知识事实源；Claude Desktop 改为读取本地仓库。
4. Claude–Cursor 分工停止执行，改为 Claude 管理与验收、Codex 默认写入与验证。
5. 原 V3.6 由 Git 历史保留；原文件名继续使用，内部规则版本升级为 V3.7。

## 二、为什么不直接复制 2073 行

`Claude_Projects指令V3.6.md` 同时承担了人格、业务方法、工作流、写作模板、质量清单、Token 管理和 Cursor 指令模板等职责。直接复制会产生四个问题：

- 常驻上下文过长，挤压真正任务需要的材料。
- 同一规则在多个章节重复，局部表述还存在冲突。
- 大量工具名在 Codex 中不存在或含义不同。
- 写文章的标准会被误用到技术说明、治理文件和普通咨询。

因此采用“常驻原则 + 条件式 SOP”的结构。

## 五、重要设计裁决

### 1. `AGENTS.md` 不是绝对最高级系统指令

它是仓库级持久指令，仍然服从平台安全规则、当前权限和用户本轮明确要求。因此，应把它理解为“这个项目的工作宪法”，不是绕过平台规则的方式。

### 2. 原始人格保留，但不压过任务本身

“带徒弟的 CEO”适合咨询、写作和知识构建；代码修复、索引检查和文件治理仍应以准确、克制、可验证为先。人格负责判断风格，不负责制造固定格式。

### 3. 真实比冲击力优先

原指令多次强调“反常识”和案例冲击力。迁移后明确裁决：

> 没有证据的冲击力，是知识库的负债。

不得为了标题、金句或故事效果编造比例、数据、人物对话和创始人反思。真实案例资料不足时，可以使用明确标注的“示意案例”，或先停在框架层。

### 4. 避免把咨询流程变成提问障碍

保留苏格拉底式提问，但仅在答案确实依赖用户关键选择时使用。用户已经给出清楚目标时，Codex 应直接行动。

### 5. 不自动做高影响外部动作

本地修改和验证属于正常执行；提交、推送、发布、删除和跨仓库写入必须遵循用户授权及当前权限。原指令中的“自动提醒同步 GitHub”不再变成每次交付的固定话术。

## 六、双管理后的标准闭环

1. Claude Desktop 读取本地文件，与松阳讨论并完成内容裁决。
2. Claude 用任务模板创建到 `协作任务/待执行/`。
3. 松阳在 Codex 中要求执行任务 ID。
4. Codex 修改本地正式文件、验证并转入 `待验收/`。
5. Claude 读取实际修改文件和执行报告，给出通过、小修或需裁决。
6. 通过后归档到 `已完成/`，必要时更新 `项目状态.md`。

简单且完全在 Codex 中提出的任务不强制走任务单；只有跨工具交接、长期跟踪或需要正式验收时使用。

## 七、建议的回归验证

用以下五类任务各跑一次，观察 `AGENTS.md` 是否达到预期：

1. 快速咨询：“我这个判断对不对？300 字内回答。”
2. CEO 指导：“团队一直追短期收入，怎么调整？”
3. 洞察讨论：“我发现即时反馈可能削弱长期坚持。”
4. 新文档写作：“【写作】把某个已验证洞察沉淀为术层文档。”
5. 文档维护：“修订一篇已有文档并同步 YAML 索引，但不要提交。”

重点观察：

- 是否先读了真正相关的项目文件。
- 是否减少了机械的模式声明和固定模板。
- 是否会直接执行本地修改。
- 是否守住案例真实性和双库边界。
- 是否准确区分“正文已修改”和“RAG 已重建”。

## 八、后续迭代原则

`AGENTS.md` 应保持稳定，只放跨任务通用规则。出现以下情况时再修订：

- 同一种错误在多个任务中重复出现。
- 项目目录、治理协议或索引机制发生正式变化。
- 某个常用流程已经稳定到值得成为全局纪律。

单次任务偏好不要立刻写进 `AGENTS.md`；优先放在当前对话或对应 SOP。这样可以避免项目指令再次膨胀成难以维护的“大一统提示词”。
